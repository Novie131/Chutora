# Security Test（授權動態安全測試）

像攻擊方那樣實際測試**你自己、已授權**的專案，確認漏洞是否真的可利用。實際執行交給 `security-test` 子 agent；這份 skill 是它照的協定與流程。

## 為什麼要動態測試

靜態審查（security-review）只能到「很可能有問題」。有些漏洞只有把系統跑起來、送真實請求才看得出來；有些靜態疑點其實打不穿。動態測試把「可疑」變成「已驗證可利用」或「已排除」，讓修補有優先序。

## 授權是前提，不是形式

**每次開工第一步**，確認並在回報開頭覆述：

- **目標**是使用者擁有或明確授權的嗎？
- **環境**是隔離的 dev／staging／sandbox 嗎？疑似 production 就停下確認。
- **範圍**哪些要測、哪些不要碰（第三方服務、真實金流／郵件、他人資料）。

任何一點不清楚：先問，不要動手。這不是官僚流程——未授權的測試在很多地方本身就是違法行為，界線必須硬。

## 硬界線

- 只打授權目標，只在隔離環境，不碰 production（除非使用者明確要求且理解風險）。
- 不外送使用者的程式碼、資料、憑證。
- 不破壞、不植後門、不留持久影響；測試資料測完清除。
- 產出給防禦用，PoC 以「足以證明與修補」為度，不做可直接打別人的武器化工具。

## 測試流程

1. 以 `security-review` 的發現清單為重點；無清單則先做輕量偵察。
2. 每個假設做**最小、可控**的驗證，先低風險手法，確認後視需要加深。
3. 記錄每次嘗試（送什麼、回什麼、能否重現），分清觀察與推論。
4. 卡住就停、回報，不無限加大力道。

## 常見面向（取專案相關的）

認證繞過、越權／IDOR、注入（SQL／命令）、SSRF、不安全的檔案上傳、業務邏輯漏洞、設定錯誤、祕密是否可由外部取得。工具用唯讀、本機、可控的為主。

## 回報格式

見 `security-test` agent 的回報格式：覆述授權與範圍 → 已驗證的問題（重現／證據／影響／修補）→ 試過但無法利用 → 清理紀錄。
